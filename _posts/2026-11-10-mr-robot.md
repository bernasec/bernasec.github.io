Write-up da máquina de CTF <a href="https://tryhackme.com/room/mrrobot">TryHackMe - Mr Robot</a>, baseada na série hacker sendo um desafio de nível medio. O objetivo é bem simples de entender: encontrar 3 chaves escondidas na máquina, cada uma representando um nível de acesso diferente.

>Vamos utilizar aqui as ferramentas Kali, SquawkerVPN, Hydra, CyberChef, Hashes.com e GTFOBins.

<p>
Antes de qualquer enumeração mais pesada, vale sempre checar o <strong>robots.txt</strong> do servidor, prática clássica de reconhecimento web. E nessa máquina ele já entrega praticamente o caminho das pedras:
</p>

```
User-agent: *
fsocity.dic
key-1-of-3.txt
```
<img src="..\assets\img\mrrobot\01-flag1-key1.png"><br>

<p>
<strong>key-1-of-3.txt</strong> nos dá de bandeja a primeira flag: <code>0734****************724b9</code> (censurada, pra não entregar de graça pra quem ainda tá resolvendo).
<br>
Já o <strong>fsocity.dic</strong> é uma wordlist enorme, aparentemente montada em cima do conteúdo da Wikia/fandom da série, cheia de palavras soltas tiradas do HTML da página (nomes de variáveis JS, classes CSS, personagens como Elliot e Robot, etc). Baixei o arquivo com <code>curl</code> e, como ele vem com muita linha repetida, rodei um <code>sort -u</code> pra limpar antes de usar em qualquer ataque de força bruta:
</p>

```
curl 10.65.174.119/fsocity.dic > dic.txt
sort -u dic.txt -o dic_bom.txt
rm dic.txt
```

<div id="forca-bruta">
<h3>Força bruta no login</h3>
<p>
Ao escanear a máquina encontrei duas portas interessantes: SSH e um servidor web rodando <strong>WordPress</strong> (wp-login.php). Tentei uma primeira rodada de força bruta via SSH com o Hydra, mas sem sucesso, o foco real acabou sendo o login do WordPress mesmo.
</p>
<p>
Antes de atacar o login, rodei um <code>dirbuster</code> rápido pra mapear diretórios/arquivos do site, e com o próprio código-fonte da página de login (e um pouco de OSINT na série) dava pra inferir o usuário <strong>Elliot</strong>. Com o usuário em mãos e o <em>dic_bom.txt</em> como wordlist de senhas, usei o Hydra contra o formulário de login do WordPress:
</p>

```
hydra -l Elliot -P dic_bom.txt 10.65.174.119 http-post-form "/wp-login.php:log=^USER^&pwd=^PASS^&wp-submit=Log+In:F=ERROR"
```

<img src="..\assets\img\mrrobot\02-hydra-wp-sucesso.png"><br>

<p>
Depois de um tempo rodando, o Hydra encontrou a combinação válida: usuário <strong>Elliot</strong> e senha <strong>ER28-0652</strong>.
</p>
</div>

<div id="acesso-wp-admin">
<h3>Acesso ao wp-admin</h3>
<p>
Com as credenciais em mãos, login direto no <code>/wp-admin/</code>. A versão do WordPress instalada era a <strong>4.3.1</strong>, rodando o tema <strong>Twenty Fifteen</strong>.
</p>
<img src="..\assets\img\mrrobot\03-wp-dashboard.png"><br>
<p>
Um usuário com papel de Administrador no WordPress consegue, por padrão, editar os arquivos PHP do tema ativo direto pelo painel (Aparência > Editor) ou enviar um novo tema/plugin. Essa é justamente a vulnerabilidade clássica explorada aqui: upload/edição de PHP por usuários Admin+, que vira execução de código no servidor.
</p>
<img src="..\assets\img\mrrobot\04-wpscan-vulnerabilidade.png"><br>
</div>

<div id="reverse-shell">
<h3>Da shell web para o usuário daemon</h3>
<p>
A ideia é simples: pegar uma reverse shell em PHP pronta (usei a clássica <strong>php-reverse-shell</strong> do pentestmonkey), trocar o IP e a porta pelos da minha máquina, e fazer o servidor executar esse código.
</p>
<p>
Minha primeira tentativa foi subir o arquivo direto como "tema" pela opção de Upload Theme, mas falhou, já que o WordPress espera um pacote .zip válido e não um .php solto (erro <code>PCLZIP_ERR_BAD_FORMAT</code>).
</p>
<p>
O caminho que funcionou foi ir em <strong>Aparência > Editor</strong> e sobrescrever o conteúdo do template <strong>404.php</strong> do tema ativo com o código da reverse shell, apontando pro meu IP e pra uma porta liberada de saída (testei 4444 e acabei usando a 80/53 pra evitar bloqueio de firewall).
</p>
<img src="..\assets\img\mrrobot\05-edit-404-theme-editor.png"><br>
<p>
Com o arquivo salvo, deixei um listener do <code>netcat</code> esperando a conexão:
</p>

```
rlwrap nc -lvnp 53
```

<p>
E para disparar o payload, bastou forçar um erro 404 no site, acessando o próprio arquivo do tema (ex: <code>/wp-content/themes/twentyfifteen/404.php</code> ou via <code>/wp-content/themes/index.php/404.php</code>, dependendo de como o roteamento do WordPress responde).
</p>
<img src="..\assets\img\mrrobot\06-reverse-shell-daemon.png"><br>
<p>
Shell recebida como o usuário <strong>daemon</strong>. Como de praxe, a shell inicial vem sem TTY interativo, então rodei o truque de sempre pra estabilizar:
</p>

```
python -c 'import pty; pty.spawn("/bin/bash")'
```
</div>

<div id="pivot-robot">
<h3>Pivotando para o usuário robot</h3>
<p>
Com shell estável, parti pra enumeração de <code>/home</code>. Lá encontrei o diretório do usuário <strong>robot</strong>, contendo <code>key-2-of-3.txt</code> (segunda flag) e <code>password.raw-md5</code>. A flag, porém, só pode ser lida pelo dono do arquivo (<em>Permission denied</em> pra daemon), então o caminho é conseguir acesso como robot mesmo.
</p>
<img src="..\assets\img\mrrobot\07-password-raw-md5.png"><br>
<p>
O arquivo <code>password.raw-md5</code> trouxe o hash: <code>c3fcd3d76192e4007dfb496cca67e13b</code>. Joguei esse hash no Hashes.com (identificação + quebra) e ele retornou a senha em texto puro:
</p>
<img src="..\assets\img\mrrobot\08-hash-crackeado.png"><br>
<p>
Hash MD5 simples, com a senha do usuário robot. Com isso, fiz login direto via SSH:
</p>

```
ssh robot@10.65.149.55
```

<img src="..\assets\img\mrrobot\09-ssh-robot-login.png"><br>
<p>
Login certo, e com isso dá pra ler o conteúdo de <code>key-2-of-3.txt</code>, nossa segunda flag.
</p>
</div>

<div id="privesc-root">
<h3>Escalando para root</h3>
<p>
Última etapa: virar root. O primeiro passo de qualquer escalonamento de privilégio em Linux é checar binários com a flag <strong>SUID</strong> setada:
</p>

```
find / -perm -4000 2>/dev/null
```

<p>
Entre os binários listados, um chamou atenção: <code>nmap</code> com SUID bit ativo, o que é incomum e perigoso, já que versões mais antigas do nmap possuem um modo interativo que pode ser abusado pra ganhar uma shell com os privilégios do dono do binário (nesse caso, root). Fui conferir no <a href="https://gtfobins.org/gtfobins/nmap/">GTFOBins</a> pra confirmar a técnica:
</p>
<img src="..\assets\img\mrrobot\10-gtfobins-nmap.png"><br>

```
nmap --interactive
nmap> !sh
```

<img src="..\assets\img\mrrobot\11-root-key3.png"><br>
<p>
E pronto, shell como <strong>root</strong>. Bastou ir até <code>/root</code> e ler a última flag, <code>key-3-of-3.txt</code>, fechando a máquina.
</p>
</div>

<div id="resumo">
<h3>Resumo</h3>
<p>
Máquina muito didática pra quem está começando em CTF/pentest web, por reunir em sequência vários fundamentos: OSINT básico via <code>robots.txt</code>, construção/limpeza de wordlist, força bruta de formulário de login com Hydra, abuso de funcionalidade administrativa do WordPress para execução remota de código, pivotagem entre usuários via hash crackeado e, por fim, escalonamento de privilégio clássico via binário SUID mal configurado.
</p>
<img src="..\assets\img\mrrobot\12-badge-final.png"><br>
</div>
